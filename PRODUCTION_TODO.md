## Deploying to the hosted Supabase project

The repo isn't linked to a project (no `supabase/.temp/project-ref`); deploys are by hand. Everything below is committed on `dev-joe` but **not yet applied to any hosted project**. Don't run it against the demo project's real data without a backup, and not against a production project until it's a separate, fresh one.

1. **Back up first** (dashboard → Database → Backups, or `pg_dump`).
2. **Set the secret** `DARAJA_CALLBACK_SECRET` (long random string; `openssl rand -hex 32`) in the project's edge function secrets, and make sure `DARAJA_CALLBACK_URL` points at the deployed `mpesa-callback`.
3. **Apply migrations in order** (`supabase db push`, or paste into the SQL editor):
   `20261021000000_student_tenant_consistency` · `20261021000001_documents_photos_grades_audit` · `20261021000002_payments_server_only` · `20261022000000_payment_method_cheque` · `20261022000001_record_payment` · `20261022000002_login_lookup_rate_limit` · `20261022000003_next_login_number` · `20261023000000_exam_marks_publication` · `20261023100000_learner_archive`.
   The last one moves existing published exams into `mark_publications` for every class and subject that has marks, so nothing already published disappears.
   The first migration prints a WARNING for any existing rows that already break the cross-school rule; read them.
4. **Redeploy the edge functions that changed**, `--no-verify-jwt` where config.toml says so: `invite-admin`, `invite-org-admin`, `provision-guardian`, `provision-student`, `mpesa-callback`, `mpesa-stk-push`, `resolve-login-id`. The functions and the web/mobile builds go together: the new sign-in screens read `display_name`, so deploy `resolve-login-id` first, then the web app and new mobile builds.
5. **Run the checks** against a copy of the database: `supabase/rls-checks/tenant_isolation.sql`, `fees.sql`, `exams_homework.sql` and `learners.sql`.
6. **Existing accounts keep their passwords.** Accounts created before this on a hosted project still have `figbloom-dev` (fine for demo accounts; rotate any real ones).

- [x] **Record payments**: confirming a payment proof doesn't credit the invoice; no way to record cash/bank/cheque. `record_payment()` + admin Fees → "Record a payment" (cash, M-Pesa to the paybill, bank, cheque); confirming a proof records its payment.
- [x] **Exams**: admin Exams screen (web) creates, renames and deletes a term's exams. Deleting is refused once any mark is entered (`guard_exam_delete`). Exams are out of 100 only (see the open item below).
- [x] **Exam publishing is per class and subject.** `publishExam` released the whole exam school-wide, so one teacher publishing exposed every other teacher's draft marks. Now `mark_publications` holds one row per exam, class and subject; `publish_marks()` / `unpublish_marks()` check the caller teaches it and write an audit event; `mark_read` and `class_means_for_exam` follow it. Teachers can withdraw published marks, on web and in the teacher app. `exams.published_at` is kept in sync by a trigger for the screens that still read it. Checked by `supabase/rls-checks/exams_homework.sql` (33 checks) and in a browser (admin creates, teacher publishes one class and subject, the learner sees only that subject, withdrawing hides it again).
- [x] **Homework**: teachers set, edit and delete homework for classes and subjects they teach (web and teacher app). Learners see their own class's homework and mark it handed in; the teacher sees "n of class size". The assignment policies used to let any teacher write any homework; they now check the class and subject assignment.
- [ ] **Exams out of other totals**: every screen assumes marks are percentages, so exams can only be created out of 100. Supporting 50 or 200 means a total per exam and converting to a percentage everywhere marks are shown, graded or averaged (Gradebook, class means, learner, parent and report views).
- [x] **Family results while a term is being published.** Parent and learner Results screens (web and both mobile apps) now have an exam switcher: one pill per exam the learner has results for, newest first, each saying how many subjects are out ("End of Term 3 · 1 subject", "Mock 1 · 9 subjects"). The list comes from the marks the learner can actually read, so an exam only another class has published no longer replaces their results with an empty page. The Home headline mean says how many subjects it covers, and a one-subject exam no longer claims a strongest and weakest. The phone app only caches the newest exam, so opening an earlier one needs a connection (it says so and offers Try again). Verified in a browser (learner, parent, phone width) and on the emulator (parent and learner apps, including offline). Still true: the Home mean for a half-published exam is a mean over the subjects out so far.
- [ ] **Homework in the teacher app** types the due date as YYYY-MM-DD (no date picker yet), and was only compiled and type-checked, not run on a device.
- [x] **Payment screens no longer fake it.** Web (parent + student Fees) and mobile (parent Pay) used a timer that said "KSh X received" and invented failures. They now call `mpesa-stk-push` (shared `payWithMpesa`) and show only what the payment row says; "received" only when Safaricom's confirmed callback has set it. When M-Pesa isn't available they show the school's paybill/till/bank details instead of pretending; a payment still unanswered after 90 s says "we haven't heard back" and never invites a second payment. Hard-coded demo phone number removed. Verified in a browser and on the emulator against the real local functions (unavailable path) and a simulated callback (success/failure); **the happy path has never run against Safaricom**.
- [ ] **Go live with real M-Pesa**: needs Safaricom Daraja credentials (`DARAJA_*`, `DARAJA_CALLBACK_SECRET`) on the production project, a sandbox end-to-end test (prompt → PIN → callback → balance), then production credentials. The parent app can send a pasted confirmation SMS and/or a photo from the gallery as proof of payment; a PDF is still web-only (the apps have a photo picker, not a document picker).
- [ ] **1000-row cap**: no query is paginated; reports, dashboards and people lists are silently truncated in large schools. Started: `fetchAllPages()` in shared; admin Fees and the billing run use it.
- [x] **Attendance loss.** Web said "register is in" before the write finished and only showed an error toast afterwards, with nothing queued, so a failed write lost the register. It now waits for the real result, holds the register on the device only when the failure is a connection or server-trouble one (so it sends itself later), and shows the server's reason, without pretending it was saved, when the server refuses it. The phone app queued every failure, including refusals that could never succeed; it now makes the same distinction. The same applies to marks, class messages and CBE results in the teacher app. Checked in a browser (server unreachable then back; server refusing) and on the emulator (register submitted in airplane mode: 0 rows on the server, then all 42 about 35 seconds after reconnecting, untouched).
- [x] **Offline queue bugs.** `flush()` wrote back the list it read at the start, so anything queued while it was sending was lost; it stopped at the first failure, so one refused write blocked every one behind it; the queue was one list per device, so a second teacher on the same phone sent (and saw) the first one's register; and nothing drained at startup. Now: every change re-reads the stored list first; a write the server refuses is set aside as "rejected" (kept, shown to the teacher with the reason, never retried) while the rest keep going, and a connection or server problem stops the run and keeps order; each write is stamped with the signed-in user; only one drain runs at a time; and both teacher apps drain on load, when the connection returns or the app comes to the foreground, and every minute. 18 unit tests. **Still open:** the driver's GPS-ping queue gets the refusal fix but is not scoped to a user and has no notice for refused pings (they pile up quietly on the phone); refused items are only discarded by hand; unsent writes stay on the device after sign-out for that user's next sign-in (they are not deleted).
- [x] **Adding staff/learners/parents fails after any deletion, and past 1,000 learners.** Login IDs were numbered "how many exist + 1": `delete-account` removes staff, so the next ID collided with an existing one ("That email is already in use") and adding that role was stuck for good; in a school with over 1,000 learners every new one was counted as the 1,001st. Now one past the highest issued number (`next_login_number()`), used by `invite-admin`, `provision-guardian`, `provision-student`.
- [x] **School search gave no feedback when it failed.** The sign-in school box swallowed every error, so a down service looked like "it doesn't start searching". Web and both mobile apps now show "Searching…" at once, "No school matches that name", or "We couldn't search just now" with a retry; lookups give up after 8 seconds; slow answers can't overwrite newer ones.
- [ ] **Attendance dates are UTC.** `today()` is the UTC date, so a register taken between midnight and 03:00 in Nairobi is filed under yesterday. Fine for an 08:00 register; wrong for a night-time boarding roll call, and for the "already taken today" check.
- [x] **Which school statuses can sign in?** Decided 2026-10-26: `active`, `trial` and `overdue` can sign in (`supabase/functions/_shared/signInStatuses.ts`, used by `search-schools` and `resolve-login-id`); `onboarding`, `setup_stalled` and `suspended` stay blocked. This only gates the school picker and ID lookup: Supabase Auth itself doesn't check the tenant's status, so a suspended school's user who already knows their sign-in email can still sign in and read their data (checked on the local stack). Closing that is part of the suspended-tenant work under P0 follow-ups.
- [ ] **Local dev: the edge-function container exits and never reloads code.** `supabase_edge_runtime_figbloom` can be down after a reboot (every function, including school search, then fails with a gateway 503), and it doesn't hot-reload: after editing a function, `docker restart supabase_edge_runtime_figbloom`. Worth a line in the README.
- [x] **Deleting a learner erased their fee records.** "Delete learner" cascaded to invoices, payments, marks, attendance, CBE results and documents, so removing someone who left in Term 2 erased that family's receipts. Learners are now **archived**: `students.active` goes false (rosters, billing, attendance and dashboards already honoured it), with who and when recorded and an audit event, and nothing is removed. People has a Current / Archived switch, Archive and Restore (single and bulk). A learner with no records at all (added by mistake, a bad import) can still be deleted; the database refuses anyone with attendance, marks, fee records, CBE or course results, hand-ins or documents, and says which (`guard_student_delete`), so the API can't do what the screen no longer offers. Removing a whole school still cascades. Homework hand-in totals now count active learners only. 23 database checks (`supabase/rls-checks/learners.sql`) and browser tests. **Still open:** an archived learner can still sign in, and their parents still see them and their balance (right while fees are owed, but there is no "leave the school" step that ends access); deleting a mistaken learner leaves their login account behind (`delete-account` only removes staff); the admin People "Manage" dialog is wider than a phone screen (it was before this).
